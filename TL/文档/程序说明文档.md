## 一、系统概述

### 1.1 这套系统干什么

一台移动小车（车端）上装着：

- **TCB605 六轴机械臂**（核心执行机构）
- **D435 深度相机**（装在手端，用于识别花盆上的 ArUco 码）
- **ROH-LiteS001 灵巧手**（抓/放种子，或抓花盆柄）
- **U 型叉子**（叉起花盆，端到修剪位修剪再放回）

车端控制系统（Jetson Nano 板）通过 **MQTT 公网协议** 接收远程指令，完成两种农活：

| 任务 | 命令 | 做什么 |
|---|---|---|
| 放种子 | `seed` / `seed_place` | 从固定取种点抓一颗种子 → 识别目标花盆 → 放进去 |
| 叉花篮修剪 | `trim_pick` / `trim_place` | 把花盆叉到修剪位 → 修剪 → 放回原位 |
| 急停 | `estop` | 立即停止一切运动（锁存，需重启节点解除）|

花盆布局：**A/B 两个区域 × 4 排 × 每排 24 盆 = 192 盆**，每盆贴一个唯一 ArUco 码（`DICT_4X4_250`，ID 0..191，黑方块 54mm）。

### 1.2 软件架构

```
车端（Jetson）
├── 机械臂驱动 tl_driver          ← 厂商驱动，TCP 直连机械臂（IP 192.168.51.22:6001/7000）
├── 种子节点 tl_mock_pick_place*  ← 处理 seed/seed_place 命令
├── 叉子节点 fork_trim_mqtt       ← 处理 trim_pick/trim_place 命令
├── 示教程序（种子/叉子）          ← 逐个教 192 个花盆的姿态
└── MQTT（paho-mqtt）             ← 与远程车端/上位机通信
                    ▲
                    │ 公网 broker（116.205.245.172:1883）
                    ▼
远程车端 / MQTTBox / 上位机
```

程序之间**不直接通信**：所有节点通过 ROS2 话题/服务访问驱动（`/joint_states`、`/tl_driver/coord_transform`、ServoJ 轨迹流），机械臂 IP 只存在于驱动配置里，改 IP 只改驱动一处。

## 三、核心流程详解

### 3.1 放种子完整周期（seed / seed_place）

收到一条命令后，程序依次执行并回 4 条反馈：

```
MQTT 收: {"cmd":"seed","targetId":"A2-05"}
  │
  ▼ ① 校验（不动机械臂）
  │    estop 激活？→ 拒绝 seed:3
  │    上一条没干完？→ 拒绝 retCode:2
  │    手处于力度5全闭？→ 拒绝 retCode:2
  │    targetId 解析: A2-05 → 花盆 29
  │    29 号没示教过？→ 拒绝 seed:3（message 写明原因）
  │
  ▼ ② 反馈1: {"cmd":"seed",     retCode:1}   ← 收到命令，开始取种
  │
  ▼ ③ 取种
  │    移到取种点上方(安全高度 130mm) → 慢速下降到固定深度(final-grasp-z 68.9mm)
  │    → 灵巧手合拢(力度5, 35000)抓稳种子 → 抬起 → 回观测位
  │
  ▼ ④ 反馈2: {"cmd":"seed",     retCode:0}   ← 取种完成（种子已抓稳）
  │
  ▼ ⑤ 定位花盆（进入放置阶段，反馈命令名切换为 seed_place）
  │    去 29 号示教检测位 → D435 拍码(DICT_4X4_250, ID=28)
  │    → 连续采样取中值，算花盆相对示教时的偏移（平移补偿）
  │    采样抖动>60mm 或偏移>200mm → 失败
  │
  ▼ ⑥ 反馈3: {"cmd":"seed_place", retCode:1} ← 放置响应（识别成功，开始放置）
  │
  ▼ ⑦ 放置
  │    移到补偿后接近位 → 慢速(20°/s)移到释放位 → 手张开(0)放种子
  │    → 立刻回力度1保护握持 → 抬回接近位 → 回检测位
  │
  ▼ ⑧ 反馈4: {"cmd":"seed_place", retCode:0} ← 放置完成（终态，周期结束）
  │
  ▼ 回观测位
```

关键点：
- **4 条反馈命令名按阶段固定**：取种阶段叫 `seed`，放置阶段叫 `seed_place`；收到 `seed` 还是 `seed_place` 命令都走同一周期
- **失败**按所在阶段回 `retCode:3`（取种阶段失败 `seed:3`，放置阶段失败 `seed_place:3`），并带 message 原因
- 已放过种子的花盆**不拒绝**，重复命令照放（`retCode:2` 只用于"忙/周期未结束"）
- 周期中 `_mqtt_publish_pending` 的 `final` 参数控制 pending 命令何时释放：只有第 4 条终态反馈才允许下一条命令进入
- **运动过程中每帧检查急停**：`estop` 一到，ServoJ 轨迹流立刻中止，锁存直到重启节点

### 3.2 叉花篮修剪周期（trim_pick / trim_place）

```
trim_pick  →  去目标花盆 → U型叉叉入 → 提起花篮 → 高位搬运
              → 降落到修剪位(位置1) → 修剪 → 挪到位置2继续修 → 叉住花篮等待
trim_place →  从修剪位抬到高位 → 搬回原花盆 → 对准放下 → 抽出叉子
```

- 两段式下降由 `TL_TRIM_LOWER_CLEARANCE_MM` 控制（先高位移动，再低速下降，防花篮掉落）
- 启动时自动回观测位；`active_transfer.yaml` 存在（叉上真有花篮）时**不自动动**，必须先 `trim_place` 放回

### 3.3 示教

**为什么必须示教**：机械臂底座位置、花盆摆放都可能有细微偏差，代码不能猜。示教 = 把机械臂（手动拖拽）对准每个花盆，记录关键姿态，运行时再用相机识码做**动态补偿**。

- **种子示教**（`teach_seed.sh`）：启动自动回一次默认起始位（A 侧）→ **每个花盆手拖**：拖到该盆码清晰入镜 → 输入花盆号 → `B` 选中（存检测位，要求码稳定可见）→ 拖到花盆上方 → `A` 接近位 → 拖到放种位置 → `P` 释放位 → 下一个。`v` 一键转 B 侧（J1+180°）继续教 B 排。示教时 ServoJ 释放，程序不主动动（仅 `R` 返回键会发运动）
- **叉子示教**（`teach_fork.sh`）：拖到花篮处 → 输入号 → `B` 检测位 → `F` 接近 → `I` 插入 → `L` 提起；`W` 搬运中点 / `T` 修剪位 / `O` 观测位（全局，只教一次）
- 数字键 0-9 输入花盆号，`c` 清空，`Q` 保存退出
- 每次写入自动备份旧版到同目录 `archive/`（示教记录丢了可以找回）

## 四、标定体系（手眼标定 + 九点验证）

### 4.1 为什么要标定

D435 相机装在机械臂末端（**eye-in-hand** 结构）。程序要抓/放，必须知道"相机里看到的点"在"机械臂基座坐标系"里的位置，坐标链是：

```
p_base = T_base_tool0 × T_tool0_camera × p_camera
          ↑驱动实时给出   ↑手眼标定给出    ↑相机内参
```

- `T_tool0_camera`：**手眼矩阵**（相机在 tool0 坐标系下的位姿），来自手眼标定
- 相机内参（`camera_matrix`/`distortion`）：标定文件里有就用标定的，没有则回退用相机自报
- 标定文件：`~/tl_handeye_data/best/handeye_best.yaml`（运行程序启动时读取）

### 4.2 手眼标定流程（TL_Dobot 仓库提供）

```bash
# ① 物理准备
#    - 暂不装灵巧手（无手标定）；相机支架/线缆固定牢
#    - 棋盘格 9x6 内角点（10x7 外角/格）、方格 25mm、贴在刚性平板上、固定不动
#    - D435 640x480@30fps，不要同时开其他 RealSense 程序

# ② 采集 25-35 组（拖拽机械臂，静止 2-3 秒后按 s）
cd ~/Desktop/TL_Dobot && source /opt/ros/humble/setup.bash
source ~/Desktop/tl_robot_ros2_py-arm/install/setup.bash
colcon build --symlink-install --packages-select tl_hand_deploy
source install/setup.bash
ros2 launch tl_hand_deploy handeye_collect.launch.py

# ③ 求解（exit_code=0 才通过全部质量门）
DATASET=~/tl_handeye_data/session_实际时间
ros2 run tl_hand_deploy tl_handeye_calibrate "$DATASET"
echo "exit_code=$?"

# ④ 验收并部署
cat "$DATASET/calibration/handeye_accepted.yaml"   # quality_checks 全 true
cp "$DATASET/calibration/handeye_accepted.yaml" ~/tl_handeye_data/best/handeye_best.yaml
```

采集分布要求：棋盘格中心覆盖九宫格 ≥5 格（预览 `coverage=N/9`）、相机距离覆盖 0.3/0.4/0.5/0.6m、绕两个正交方向各覆盖 30-60°、既要变方向也要变位置（只绕法兰转或只平移都不行）。

**质量门要点**（默认门槛）：有效样本 ≥20（建议 25-35）、全局重投影 RMS ≤0.8px、基座标定板平移 RMS ≤5mm / 最大 ≤10mm、旋转 RMS ≤0.5°、TCP 平移跨度 ≥120mm、旋转跨度 ≥40°、留一法平移变化 ≤5mm。不合格只会生成 `handeye_candidate_rejected.yaml`，**不会**被标记为可用。

### 4.3 运行程序怎么用标定

- 启动器参数 `--calibration ~/tl_handeye_data/best/handeye_best.yaml`（`TL_CALIBRATION` 可覆盖）
- `load_calibration` 强制校验：`accepted` 必须为 true（被拒的标定只有 `--allow-rejected` 才能粗测）、RPY 约定必须 `intrinsic_xyz`
- 花盆码定位**强制 PnP**（`pnp_fallback_mm=0.0`），深度只做交叉检查——标定精度直接决定放种精度
- `--base-xy-bias-mm`（当前 `-53.2 -34.2` mm）是九点验证后叠加在基座 XY 的**常量经验补偿**
  ⚠️ 注意：该值过大说明标定或验证条件有问题（历史教训：补偿从 `[-20.7, 5.3]` 漂到 `[-85.25, -16.44]` 是警报）。重新标定后应清零补偿重测，而不是继续叠加大补偿

### 4.4 九点标定（绝对精度验证）

手眼标定"内部一致性"通过 ≠ 抓得准。九点验证是**端到端绝对精度验收**：在工作平面布 3×3 十字点（间距约 60mm），用与 tool0 同轴的短指针，逐点对比"视觉算出的目标"与"指针实际落点"：

| 验收项 | 建议目标 |
|---|---:|
| 九点 XY RMS | ≤ 5 mm |
| 九点 XY 最大误差 | ≤ 8 mm |
| Z 高度最大误差 | ≤ 5 mm |

```bash
LOG=~/tl_handeye_validation/本次九点记录.jsonl
ros2 run tl_hand_deploy tl_handeye_validate "$LOG" \
  --calibration ~/tl_handeye_data/best/handeye_best.yaml
echo "exit_code=$?"   # 0 且 .acceptance.json 的 quality_checks 全 true 才通过
```

**误差模式解读**（决定能不能补偿）：
- 九点误差方向和大小一致 → 固定偏移（tool0/指针/TCP 偏差），可常量补偿
- 误差随 X/Y 位置系统变化 → 手眼旋转/机器人坐标/支架刚性有问题，**必须重标定**，不能用均值掩盖
- 误差随机分散 → 查点击、深度、纸面反光、机械臂静止与重复定位

**铁律**：九点验证通过前，禁止启用灵巧手自动闭合与接触抓取。

### 4.5 安装灵巧手后的处理

无手标定得到的是 `T_tool0_camera`，不能直接当掌心 TCP 用。已准确测得 `T_flange_tool` 时可转换：

```bash
ros2 run tl_hand_deploy tl_convert_handeye_frame \
  ~/tl_handeye_data/best/handeye_best.yaml \
  --flange-to-tool X_MM Y_MM Z_MM RX_RAD RY_RAD RZ_RAD \
  --output ~/tl_handeye_data/grasp_tcp_camera.yaml
```

转换后必须用**掌心 TCP 重新做九点验证**。若装手导致相机支架受力/位置变化，直接重做手眼标定。

> 完整标定文档见 `TL_Dobot/docs/handeye_precision_pipeline_zh.md`。

## 五、MQTT 协议（车端协议）

### 5.1 通信参数

| 项 | 值 |
|---|---|
| Broker | 公网 `116.205.245.172:1883`（用户 `shapandevice` 密码 `qwer1234!!`）|
| 命令 topic | `node/arm/01/down`（车 → 机械臂，QoS 1）|
| 反馈 topic | `node/arm/01/up`（机械臂 → 车，QoS 1）|
| 协议 | JSON，UTF-8 |

### 5.2 命令

| cmd | targetId | 说明 |
|---|---|---|
| `seed` | 必填 | 完整放种周期 |
| `seed_place` | 必填 | 同 `seed`，完整放种周期 |
| `trim_pick` | 必填 | 叉花篮到修剪位 |
| `trim_place` | 必填 | 花篮放回原位 |
| `estop` | **不需要** | 急停，锁存直到重启节点 |

### 5.3 targetId → 花盆号映射

```
A1-01..A1-24 → 1..24      A2-01..A2-24 → 25..48
A3-01..A3-24 → 49..72     A4-01..A4-24 → 73..96
B1-01..B1-24 → 97..120    B2-01..B2-24 → 121..144
B3-01..B3-24 → 145..168   B4-01..B4-24 → 169..192
ArUco 码 ID = 花盆号 - 1（如 A2-05 = 29 号 = 码 ID 28）
```

### 5.4 retCode 语义

| retCode | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 响应命令，开始动作 |
| 2 | 位置被占 / 命令忙（上一条未完成）|
| 3 | 识别不成功 / 放置失败（带 message 原因）|

### 5.5 放种子反馈时序（4 条）

| # | 时机 | 反馈 |
|---|---|---|
| 1 | 收到命令 | `{"cmd":"seed",       "targetId":"A2-05","retCode":1}` |
| 2 | 取种完成 | `{"cmd":"seed",       "targetId":"A2-05","retCode":0}` |
| 3 | 放置响应 | `{"cmd":"seed_place", "targetId":"A2-05","retCode":1}` |
| 4 | 放置完成 | `{"cmd":"seed_place", "targetId":"A2-05","retCode":0}` |

失败：取种阶段失败回 `seed:3`，放置阶段失败回 `seed_place:3`（带 message）。

### 5.6 叉子命令反馈

每条命令两条：先 `{"cmd":"trim_pick","targetId":"...","retCode":1}`，完成后 `retCode:0`；失败 `retCode:3`。

### 5.7 急停

`{"cmd":"estop"}` → 无 targetId → 反馈 `{"cmd":"estop","retCode":0}` → 锁存：之后所有命令一律拒绝（retCode 3）→ **必须重启节点**解除。物理 E-stop 始终保留（程序急停 ≠ 断电）。

## 六、关键参数说明（种子启动器）

启动器 `run_fixed_pick_mqtt_headless.sh` 里这些参数对应程序行为：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `--basket-aruco-file` | `~/tl_mock_pick_place/basket_aruco.yaml` | 示教记录（谁教过才能用）|
| `--fixed-pick-base-mm` | `500.0 -250.94 58.1` | 固定取种点（种子盒位置）|
| `--final-grasp-z-mm` | `68.937` | 取种下降绝对高度 |
| `--observation-joints` | 6 个角度 | 观测位（启动/周期结束回这里）|
| `--servoj-speed-deg-s` | `40` | 快速移动角速度 |
| `--servoj-precision-speed-deg-s` | `20` | 放置/取种慢速 |
| `--servoj-min-duration-sec` | `0.3` | 单段运动最短时长 |
| `--use-hand` | 开 | 使用灵巧手 |
| `--hand-grasp-positions` | `35000×5 + 25000` | 抓取力度 5 |
| `--hand-open-positions` | `0×6` | 完全张开 |
| `--hand-hold-positions` | `8000×5 + 5000` | 保护握持力度 1 |
| `--basket-motion-mode` | `translation` | 花盆偏移只平移，保持示教姿态 |
| `--max-basket-shift-mm` | `200` | 花盆偏移超 20cm 判失败 |
| `--marker-sample-spread-mm` | `60` | 码采样抖动超 60mm 判脏数据 |
| `--mqtt-*` | 公网 broker | broker 地址/账号/topic（环境变量可覆盖）|

## 七、文件更新流程（改代码后）

程序用 `--symlink-install` 编译，**install 目录是 src 的软链，改源码不用重新编译**，覆盖文件 + 重启节点即可。

```bash
# Windows 传文件到 Jetson（PowerShell）
scp C:\Users\DragonAfterAll\Desktop\TL_Handback\src\tl_hand\tl_hand\mock_pick_place.py \
    nvidia@<Jetson-IP>:~/Desktop/TL_Handback/src/tl_hand/tl_hand/
# 然后重启对应节点
```

⚠️ 常见坑：Jetson 上文件被旧版本覆盖（对比大小/`grep` 关键字确认版本）。曾出现：`basket_aruco.py` 被旧版（`range(24)`、`DICT_4X4_50`）覆盖导致新教的 25-54 号"消失"——症状是启动日志 `taught marker numbers` 少了。

## 八、常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动卡住 / 连不上机械臂 | 驱动没跑或机械臂 IP 不对 | 先起驱动；IP 改在 `~/Desktop/tl_robot_ros2_py-arm/src/tl_driver/` 配置 |
| `MQTT did not accept a connection` | 公网不通 / broker 故障 | Jetson 上 `ping 116.205.245.172`，`echo > /dev/tcp/116.205.245.172/1883` 测端口 |
| MQTT reason=5 | 账号密码错 | 检查 `TL_MQTT_USERNAME/TL_MQTT_PASSWORD` |
| 反馈 retCode:3 但机械臂没动 | 目标盆没示教 / 码识别不到 | 看 message 字段；补示教 / 检查码是否 54mm 新码 |
| `taught marker numbers` 数量不对 | `basket_aruco.py` 或示教文件被旧版覆盖 | 对比文件大小；示教记录可从 `archive/` 恢复 |
| D435 无画面 / 0 samples | USB 问题 | 拔插 D435（换 USB3 口），重启节点 |
| 启动提示 `Active fork transfer state found` | 叉上真有花篮 | 发 `trim_place` 放回；空叉则删 `active_transfer.yaml` 重启 |
| 急停后所有命令被拒 | estop 锁存设计 | 重启节点 |
| 抓取/放置整体偏移（方向一致）| 固定偏移未补偿 | 九点验证确认后用常量补偿（`--base-xy-bias-mm`）|
| 偏移随位置系统变化 | 手眼标定/支架刚性有问题 | 重新手眼标定，不要用均值掩盖 |
| 标定文件被拒（`accepted: false`）| 质量门未过 | 只能 `--allow-rejected` 粗测，正式使用必须重标定 |

## 九、安全须知

1. **物理 E-stop 始终在手边**，程序级 `estop` 只是停止运动流，不是断电
2. 测试期间机械臂运动路径上不要站人
3. 示教时确认码贴正、花盆固定，否则运行时偏移补偿会失败
4. 改机械臂 IP 后：只改驱动配置一处，改完重启驱动，`ping` 通再起节点
5. 公网 broker 凭据不要外泄（当前为演示配置）
6. 九点验证通过前禁止灵巧手自动闭合与接触抓取

## 十、后续规划：VLA（视觉-语言-动作）接入

### 10.1 VLA 是什么、为什么做

当前系统是**规则化管线**：手工示教姿态 + 相机识码（ArUco）+ IK 插值 + 固定协议。它对"贴好码、位置固定"的场景可靠，但遇到新摆放、乱序花盆、动态障碍就需要重新示教/调参。

VLA（Vision-Language-Action，视觉-语言-动作模型）的目标：**模型直接看相机画面（+语言指令），端到端输出机械臂动作**，泛化到未见过的场景，比如"把种子放到 A2-05"这种自然语言指令直接驱动抓放。

### 10.2 现有系统的数据资产（VLA 训练的前提）

| 已有资产 | 说明 |
|---|---|
| 示教记录 | 每盆存了 search_pose（joint + tcp + T_base_marker + 相机帧）→ 天然的"图像-动作"配对 |
| 运行日志 | 放种/叉修剪每跑一次都是成功/失败轨迹样本 |
| 固定坐标系 | 基座坐标、观测位、取种点全局一致 → 数据可直接对齐 |

→ 后续把示教程序升级为**动作序列记录器**（记录从示教位到放置的完整 joint 轨迹 + 同步相机帧 + 语言标签），就能自动攒 VLA 训练集。

### 10.3 部署架构设想

```
                    ┌─────────────── 上位机/云端（训练 & 可选推理）───────────────┐
                    │  数据清洗 → 微调/蒸馏（OpenVLA / π0 / RDT 等）              │
                    └───────────────▲───────────────────────────────▲────────────┘
                                    │ 模型权重下发/远程推理              │ 轨迹数据上传
                    ┌───────────────┴───────────────────────────────┴────────────┐
车端 Jetson         │  VLA 推理（INT8/FP16 小模型） 或  远程推理客户端              │
                    │  输入：D435 彩色/深度流 + 关节状态 + targetId（语言化）       │
                    │  输出：动作（关节目标/末端轨迹）→ 现有运动安全层 → ServoJ     │
                    └──────────────────────────────────────────────────────────────┘
```

- **算力现实**：Orin Nano 8GB 只适合 ≤3B 量级的量化小模型；大 VLA（7B+）需要上位机 GPU 远程推理（5G/WiFi 链路，关注延迟）
- **接口不变**：MQTT 命令/反馈协议（第四章）保持不动，VLA 只替换系统内部"识码 + IK"这一段，车端协议对上层透明

### 10.4 接入路线图

1. **数据规范化**：示教/运行程序增加"轨迹记录模式"——存完整动作序列（非单姿态）、图像时间戳对齐、语言标签（"取种"、"放到 A2-05"、"叉起花盆"）
2. **模型选型试点**：按 Orin Nano 显存/算力选蒸馏版 VLA（或先跑"感知+轻量策略"的折中方案，如视觉目标检测 + 学习型放置偏移）
3. **离线评测**：用历史示教数据重放，对比 VLA 输出与真实轨迹误差
4. **影子模式**：VLA 与现有管线并行推理、只对比不执行；指标达标后再切换
5. **灰度上线**：先放种任务（低风险、可重复）→ 叉修剪 → 异常自动回退规则管线

### 10.5 风险与依赖

| 风险 | 说明 / 对策 |
|---|---|
| 算力不足 | Orin Nano 上跑不动大模型 → 量化/蒸馏或上位机远程推理 |
| 数据量不够 | 端到端 VLA 需要数千-数万条演示 → 先做自动化数据采集（规则管线批量跑 + 记录）|
| 运动安全 | VLA 输出必须经过现有安全层：`max-joint-delta` 限幅、到位校验、`estop` 兜底，**不允许绕过** |
| 标定依赖 | VLA 同样依赖相机/基座对齐，手眼标定质量依然重要 |
| 实时性 | 远程推理延迟 → 目标 <200ms 动作周期；超标则回退规则管线 |
